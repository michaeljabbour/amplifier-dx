# Amplifier

A small kernel. Everything else is a module.

 The kernel handles sessions, mount points and events, and nothing more. Providers, tools,
 the agent loop, memory and safety checks all plug into it, and a bundle decides which ones.

 Get started
 Browse the ecosystem

 How a prompt moves through Amplifier
 A prompt enters the orchestrator, which runs the agent loop and returns a response. The orchestrator calls a provider, tools and a context manager. Hooks observe every event and can block a tool call. All five module types are mounted on the kernel, amplifier-core.

### 4. Choose a root, add behaviors

A root bundle is a complete configuration (orchestrator, context manager, tools, agents). A behavior is a partial bundle that adds one capability on top of whatever root is active. Selecting a root and adding behaviors are separate commands:

 bash
 Copy

amplifier bundle list
amplifier bundle current

A bundle is a markdown file with YAML frontmatter. Include a complete root and add only what differs. The body is the system instruction; `@namespace:path` pulls in context files.

Write a custom tool in under 2 minutes using duck typing.

### 1. Implement the Tool protocol

 python
 Copy

`from amplifier_core.models import ToolResult

class WeatherTool:
 @property
 def name(self) -> str:
 return "weather"

 @property
 def description(self) -> str:
 return "Get current weather for a city"

 @property
 def input_schema(self) -> dict:
 """JSON Schema describing the arguments (RECOMMENDED)."""
 return {
 "type": "object",
 "properties": {
 "city": {"type": "string", "description": "City name"}
 },
 "required": ["city"]
 }

 async def execute(self, input: dict) -> ToolResult:
 city = input.get("city")
 if not city:
 return ToolResult(success=False, error={"message": "city is required"})
 return ToolResult(output=f"Weather in {city}: 72°F, Sunny")`
```

 Why input_schema matters

`input_schema` is what the model sees when it decides how to call your tool. The tool contract treats it as optional (it defaults to `{}`), so check required arguments inside `execute()` and return a failed `ToolResult` rather than assuming the input is complete.

### 2. Add mount function

 python
 Copy

`async def mount(coordinator, config):
 await coordinator.mount("tools", WeatherTool(), name="weather")
 return lambda: None # cleanup`
```

### 3. Register entry point

 toml
 Copy

`# pyproject.toml
[project.entry-points."amplifier.modules"]
tool-weather = "amplifier_module_tool_weather:mount"`
```

### 4. Add it to a bundle

Embed Amplifier in your application with full programmatic control.

### 1. Load, compose, prepare, run

The recommended path goes through `amplifier-foundation`: load bundles, compose them, prepare once (this downloads and activates the modules), then create sessions.

 python
 Copy

`import asyncio
from pathlib import Path
from amplifier_foundation import load_bundle

async def main():
 anchors = await load_bundle(
 "git+https://github.com/microsoft/amplifier-foundation@main"
 "#subdirectory=bundles/anchors/bundle.md"
 )
 provider = await load_bundle(
 "git+https://github.com/microsoft/amplifier-foundation@main"
 "#subdirectory=providers/anthropic-sonnet.yaml"
 )

 composed = anchors.compose(provider) # later overrides earlier
 prepared = await composed.prepare() # do once; downloads and activates modules

 session = await prepared.create_session(session_cwd=Path.cwd())
 async with session:
 response = await session.execute("Hello! What can you help me with?")
 print(response)

asyncio.run(main()) # requires ANTHROPIC_API_KEY`
```

`Bundle.compose()` takes `Bundle` objects, not dicts. `create_session()` is a coroutine that returns an initialized `AmplifierSession`; the session has `initialize()`, `execute(prompt) → str` and `cleanup()`, and works as an async context manager.

### 2. Add custom hooks

Register handler functions on the coordinator's hook registry. Event names match exactly; there is no wildcard subscription, so register once per event.

 python
 Copy

`from amplifier_core.models import HookResult

async def audit_hook(event: str, data: dict) -> HookResult:
 print(f"{event}: {data['tool_name']}")
 return HookResult(action="continue")

session = await prepared.create_session(session_cwd=Path.cwd())
session.coordinator.hooks.register("tool:pre", audit_hook, name="audit-pre")
session.coordinator.hooks.register("tool:post", audit_hook, name="audit-post")`
```

### 3. Resume a session by ID

 python
 Copy

`# Your app owns storage: keep the session ID and the transcript yourself
session = await prepared.create_session(
 session_id="user-123-session",
 session_cwd=Path.cwd(),
 is_resumed=True, # the kernel emits session:resume instead of session:start
)

# Restore conversation history into the context manager
context = session.coordinator.get("context")
for msg in historical_messages:
 await context.add_message(msg)

async with session:
 response = await session.execute(prompt)`
```

### 4. Spawn sub-sessions

A session has no `fork()` method. Sub-sessions are spawned from the prepared bundle; agents are bundles, so the child is loaded the same way.

 python
 Copy

`reviewer = await load_bundle("./agents/reviewer.md")

backend, frontend = await asyncio.gather(
 prepared.spawn(reviewer, "Analyze backend", parent_session=session),
 prepared.spawn(reviewer, "Review frontend", parent_session=session),
)
print(backend["output"], backend["session_id"])`
```

For the model to delegate on its own through the `delegate` tool, the host must register a `session.spawn` capability after `create_session()` and before `execute()`. The reference implementation is `session_spawner.py` in `amplifier-app-cli`.

 Kernel-only path

`AmplifierSession(mount_plan)` from `amplifier_core` is still valid kernel API. It requires `session.orchestrator` and `session.context` in the mount plan and only works when every module in the plan is already importable. Mount-plan `hooks` entries are module specs (`{module, source, config}`), not handler functions.

 Reference Implementation

See amplifierd for a complete HTTP/SSE host, and `examples/01_hello_world.py` and `docs/APPLICATION_INTEGRATION_GUIDE.md` in amplifier-foundation.

# Architecture

Design philosophy: kernel, not framework. Mechanism over policy.

 Complete Architecture Documentation

For in-depth architectural guides, see the official architecture documentation.

## The Four Tenets

### 1. Mechanism, Not Policy

The kernel provides capabilities and stable contracts. Behavioral decisions live outside the kernel. If teams could want different behavior, it belongs in modules.

### 2. Small, Stable, Boring

A deliberately small Rust kernel with Python bindings. Fewer changes = fewer breaking changes. Prioritizes auditability and predictability over clever implementations.

### 3. Don't Break Modules

Kernel interfaces follow sacred backward compatibility. Additive evolution for module-facing Python contracts; 2.0 was a major version only for Rust construction APIs and stricter module identity checks.

### 4. Extensibility via Composition

New capabilities come from combining modules, not accumulating kernel configuration flags. Avoids "configuration explosion" by pushing policy to the edges.

## The Linux Kernel Analogy

Amplifier mirrors Linux kernel concepts:

 |

 | Linux Concept | Amplifier Analog | Purpose

 | Ring 0 kernel | `amplifier-core` | Mechanisms only, never policy

 | Syscalls | Session operations | Few, sharp APIs

 | Loadable drivers | Modules | Compete at edges

 | Signals/Netlink | Event bus / hooks | Observe and control

 | /proc & dmesg | JSONL logs | Single canonical stream

 | Capabilities | Approval system | Deny-by-default

 | Scheduler | Orchestrator modules | Swap execution strategies

 | VM/Memory | Context manager | Conversation memory

## Core concepts

### Coordinator

Infrastructure context injected into all modules.

- `session_id` — Unique identifier

- `config` — Session configuration

- `mount(mount_point, module, name)` — Register module

- `hooks.emit(event, data)` — Fire events

- `register_capability()` / `get_capability()` — Share capabilities

### Mount Plan

Configuration specifying which modules to load.

`{
 "session": {"orchestrator": "loop-basic", "context": "context-simple"},
 "providers": [{"module": "provider-anthropic"}],
 "tools": [{"module": "tool-filesystem"}]
}`
```

### Session Lifecycle

- Load modules from mount plan

- Call `mount()` on each, then `on_session_ready()`

- Execute prompts via orchestrator

- On cleanup: emit `session:end`, then run cleanup callables in reverse order

## Module Distribution Architecture

Understanding how modules are distributed and resolved is critical for building applications with amplifier-core.

 Key Insight

Every module type registers a `mount` function under the `amplifier.modules` entry-point group. Where the code comes from (installed package, git cache, local path) is decided by the app's module-source resolver.

### Two-Tier Module System

 |

 | Distribution Method | Module Types | Location | Resolution

 | Entry Points
 | All module types
 | Python package metadata (`amplifier.modules` group)
 | `importlib.metadata`

 | Source Resolver
 | Any module type
 | Wherever the resolver points (git clones are cached under `~/.amplifier/cache/`)
 | A `module-source-resolver` mounted on the coordinator by the app or foundation

 | Filesystem
 | Any module type
 | `amplifier-module-*` directories
 | `ModuleLoader` `search_paths` or `AMPLIFIER_MODULES`

### Entry Points (`amplifier.modules`)

Modules installed as Python packages are registered via entry points:

`# Table "Installed Modules (via entry points)": Name, Type, Source, Origin, Description
amplifier module list

# Filter by type: orchestrator, provider, tool, agent, context, hook
amplifier module list --type provider

# Show where a module ID resolves from
amplifier source show tool-bash`
```

### Module Cache

Git-based modules (orchestrators, tools, hooks, providers) are cloned to the cache:

`# Cache location
~/.amplifier/cache/

# Structure (directories named <repo>-<hash>)
cache/
 ├── amplifier-core-<hash>/
 ├── amplifier-module-loop-streaming-<hash>/
 └── amplifier-module-tool-filesystem-<hash>/`
```

### Module Loading Priority

When loading a module, the loader checks sources in this order:

- Already loaded — A module this loader has already loaded is reused

- Source resolver — The mounted module-source resolver, given the mount plan's `source`

- Without a resolver — Entry points (`amplifier.modules`), then filesystem search

### Required Components

External applications can provide up to three optional policy components:

### 1. ModuleLoader

Custom loader to resolve modules from your preferred sources.

`from amplifier_core import ModuleLoader

class LocalLoader(ModuleLoader):
 """Serve some modules from in-process mount functions."""

 def __init__(self, local_mounts, **kwargs):
 super().__init__(**kwargs)
 self.local_mounts = local_mounts # {module_id: async mount(coordinator, config)}

 async def load(self, module_id, config=None, source_hint=None, coordinator=None):
 mount_fn = self.local_mounts.get(module_id)
 if mount_fn is None:
 # Fall back to the default resolution
 return await super().load(module_id, config, source_hint, coordinator)

 async def mount_with_config(coord):
 return await mount_fn(coord, config or {})

 return mount_with_config # load() returns a mount callable`
```

### 2. ApprovalSystem

UI/UX for user consent on tool execution.

`from amplifier_core.approval import ApprovalSystem # the protocol

class MyApprovalSystem:
 async def request_approval(self, prompt: str, options: list[str],
 timeout: float, default: str) -> str:
 # Show UI dialog, return the chosen option
 return await show_approval_dialog(prompt, options, timeout, default)`
```

### 3. DisplaySystem

Rendering for messages that hooks show to the user. Tool calls and streaming are rendered from hook events.

`class MyDisplaySystem:
 def show_message(self, message: str, level: str, source: str = "hook"):
 # Synchronous. level is "info", "warning" or "error".
 # Render message to your UI
 pass

# The protocol has no show_tool_call: render tool calls
# from tool:pre / tool:post hooks instead.`
```

### Creating an AmplifierSession

`from amplifier_core import AmplifierSession

# The mount plan is a plain dict
config = {
 "session": {"orchestrator": "loop-streaming", "context": "context-simple"},
 "providers": [{"module": "provider-anthropic", "config": {"default_model": "<model>"}}],
 "tools": [{"module": "tool-filesystem"}, {"module": "tool-bash"}],
}

# Create session with your policy components
session = AmplifierSession(
 config,
 approval_system=MyApprovalSystem(), # Your approval UI
 display_system=MyDisplaySystem(), # Your message renderer
)
# The loader= constructor argument is ignored by the Rust-backed session;
# attach a custom loader through the coordinator before initialize().
session.coordinator.loader = LocalLoader(local_mounts, coordinator=session.coordinator)

await session.initialize() # required before execute()
try:
 # Run a prompt
 result = await session.execute("What files are in this directory?")
finally:
 await session.cleanup()`
```

`async with AmplifierSession(config) as session:` is equivalent to the `initialize()` / `cleanup()` pair when no custom loader is needed.

### Production Configuration

When deploying agents for code generation or complex tasks, configure providers defensively:

 Critical: Token Limits

A low `max_tokens` is insufficient for code generation. When the model hits the limit mid-stream, it truncates output producing incomplete JSON tool calls. `provider-anthropic` 1.0.0 defaults to the model's output ceiling, so this only bites if you set a lower cap.

Keys and defaults below are from the `provider-anthropic` 1.0.0 configuration reference. Other providers have their own keys and defaults; check each provider's README.

 |

 | Setting | Default | Recommended | Why

 | `max_tokens`
 | model ceiling
 | Leave unset, or cap at 8192+
 | Output token cap; a low cap truncates tool calls during code generation

 | `temperature`
 | 0.7
 | Default
 | Ignored by non-sampling models (Sonnet 5, Opus 4.7+)

 | `timeout`
 | `null` (no deadline)
 | Set a value in seconds only if you need a request deadline
 | By default a request waits for completion

 python
 Copy

`# Production configuration for coding agents
config = {
 "session": {
 "orchestrator": "loop-streaming",
 "context": "context-persistent"
 },
 "providers": [{
 "module": "provider-anthropic",
 "config": {
 "default_model": "<model>",
 "max_tokens": 8192, # Explicit output cap (default: model ceiling)
 "temperature": 0.7, # The default; ignored by non-sampling models
 }
 }],
 "tools": [
 {"module": "tool-filesystem"},
 {"module": "tool-bash"}
 ]
}`
```

### Hook Events for Streaming UI

Subscribe to hook events for real-time UI updates:

 |

 | Event | Description | Payload

 | `content_block:start` | Text block begins | `{index, type}`

 | `content_block:delta` | Streaming text chunk | `{index, delta}`

 | `content_block:end` | Text block complete | `{index}`

 | `thinking:delta` | Extended thinking chunk | `{delta}`

 | `thinking:final` | Thinking complete | `{content}`

 | `tool:pre` | Before tool execution | `{tool_name, tool_input, tool_call_id}`

 | `tool:post` | After tool execution | `{tool_name, tool_input, tool_result}`

 | `provider:request` | LLM API call starts | `{provider, messages, model}` per the orchestrator contract; `loop-streaming` 1.0.0 emits `{provider, model, iteration}`

 | `provider:response` | LLM API call ends (listed in the orchestrator contract; the current `loop-streaming` does not emit it, so watch `llm:response` too) | `{provider, response, usage}`

## Troubleshooting Common Errors

Common issues when integrating with amplifier-core and their solutions:

### `Missing required arguments: ['content']`

Cause: Token limit hit mid-generation, truncating JSON output.

Fix: If you set `max_tokens` in provider config, raise it to 8192+ or remove it (`provider-anthropic` 1.0.0 defaults to the model ceiling).

`"providers": [{
 "module": "provider-anthropic",
 "config": {"max_tokens": 8192}
}]`
```

### `tool_use.name: String should have at least 1 character`

Cause: LLM generated empty tool name (hallucination).

Fix: Add sanitization layer in your provider integration:

`# Sanitize empty tool names before API call
if not tool_call.get("name") or not tool_call["name"].strip():
 tool_call["name"] = "unknown_tool"
 logger.warning(f"Fixed empty tool name")`
```

### `ToolCallBlock has invalid name`

Cause: Same as above - LLM returned malformed tool call.

Fix: Validate tool calls before execution and add a sanitization hook.

### `'tuple' object has no attribute 'get'`

Cause: Patch/modification applied to incompatible module type (cached vs local).

Fix: Check module implementation matches expected interface. Clear the cache (`~/.amplifier/cache`):

`amplifier reset --remove cache -y`
```

### LLM Edge Case Handling

LLMs can generate invalid tool calls. Your integration should sanitize these defensively:

 python
 Copy

`def sanitize_tool_calls(tool_calls: list) -> list:
 """Clean up malformed LLM tool calls before execution."""
 sanitized = []
 for tc in tool_calls:
 # Fix empty names
 name = tc.get("name", "").strip()
 if not name:
 name = "unknown_tool"
 logger.warning(f"Fixed empty tool name for id={tc.get('id')}")

 # Ensure arguments is a dict
 args = tc.get("arguments") or tc.get("input") or {}
 if isinstance(args, str):
 try:
 args = json.loads(args)
 except json.JSONDecodeError:
 args = {"raw": args}

 sanitized.append({
 "id": tc.get("id"),
 "name": name,
 "arguments": args
 })
 return sanitized`
```

# API Reference

Complete documentation for module developers.

 Complete API Reference

For the full API documentation including all contracts and interfaces, see the official Developer Guide.

 Contracts

Python modules implement Protocols (structural typing, no inheritance). The same contracts exist as Rust traits, gRPC services and WASM interfaces.

#### Provider LLM Backend

 `name: str`
 `get_info() → ProviderInfo`
 `list_models() → list[ModelInfo]`
 `async complete(request: ChatRequest, **kwargs) → ChatResponse`
 `parse_tool_calls(ChatResponse) → list[ToolCall]`

#### Tool Agent Capability

 `name: str`
 `description: str`
 `input_schema: dict` (recommended)
 `execute(input: dict) → ToolResult`

#### Orchestrator Execution Loop

 `async execute(prompt, context, providers, tools, hooks, **kwargs) → str`
 (the kernel passes `coordinator=` as a keyword)

#### ContextManager Memory

 `add_message(message)`
 `get_messages_for_request(token_budget=None, provider=None) → list`
 `get_messages() → list`
 `set_messages(messages)`
 `clear()`

#### HookHandler Observe and control

 `async __call__(event: str, data: dict) → HookResult`
 registered with `coordinator.hooks.register(event, handler, priority=0, name=None)`

Hooks observe events and optionally modify behavior via HookResult.

 python
 Copy

`async def my_hook(event: str, data: dict) -> HookResult:
 if event == "tool:pre" and "rm -rf" in str(data.get("tool_input")):
 return HookResult(action="deny", reason="Blocked")
 return HookResult(action="continue")`
```

### HookResult Actions

 `continue`
 Proceed normally (default)

 `deny`
 Block with reason

 `modify`
 Alter event data

 `inject_context`
 Add message to context

 `ask_user`
 Pause for approval

When several hooks respond to one event, precedence is `deny > ask_user > inject_context > modify > continue`. Handlers run in priority order (lower number first); a handler that raises is logged and skipped. amplifier-core 2.0 added `HookResult.context_injections`, a list of `ContextInjection` items.

40+ hookable events covering the entire agent lifecycle (43 canonical events, verified against amplifier-core 2.0.2, November 2026). The tables below list 23 of them; the rest are `plan:*`, `thinking:*`, `orchestrator:complete`, `execution:*`, `user:notification`, `artifact:*`, `policy:violation`, `cancel:*`, `module:*`, `provider:retry` / `throttle` / `tool_sequence_repaired` / `resolve` and `context:compaction`. Events are logged as JSONL for debugging and observability.

### Session Lifecycle

 |
 | Event | When | Data

 | `session:start` | First execute() of a new session | session_id, parent_id, metadata (optional)

 | `session:end` | Session cleanup, before module cleanup | session_id, status

 | `session:fork` | Child session initialized | parent, session_id

 | `session:resume` | First execute() of a resumed session | session_id, parent_id, metadata (optional)

The redacted mount plan appears as a `raw` field on the `session:start`, `session:resume` and `session:fork` payloads when `session.raw` is true. `session:config` is not one of the 43 canonical events: amplifier-core 2.0.2 contains a helper that would emit it, but no emission was verified in that build, so do not subscribe to it expecting delivery.

Emitters: the kernel emits the `session:*` events above, `module:load_failed` and `module:on_session_ready_failed` (a failed mount or `on_session_ready` does not abort the session), and `cancel:completed`. The orchestrator and provider modules emit the prompt, provider, tool, content-block and `llm:*` events, so what you see depends on the loop module in use.

A bundle is a markdown file with YAML frontmatter (or a plain `.yaml` file with no body) that compiles to a mount plan. Bundles replaced profiles and collections, which no longer exist in Amplifier. Verified against `amplifier-foundation` main (2026-11-17) and `amplifier-app-cli` 2026.09.06.

### Roots and Behaviors

 |

 | Kind | What it is | How you use it

 | Root bundle | A complete configuration: it chooses `session.orchestrator` and `session.context` and carries the system instruction. A root is never composed as a behavior. | Select one: `amplifier bundle use <name>`

 | Behavior | An ordinary bundle file, by convention `behaviors/<name>.yaml`, that is deliberately partial: it contributes agents, context and optionally tools and hooks, and does not choose a provider, orchestrator, context manager or root instruction.  |

 | Root | Namespace | Notes

 | `anchors` | `anchors` | Recommended base for a new complete host, and the default root in the installed build (2026.09.06). Six agents: `anchors:explorer`, `architect`, `builder`, `debugger`, `git-ops`, `researcher`.

 | `anchors-amp-dev` | `anchors-amp-dev` | A thin root that includes `anchors` plus an Amplifier-development behavior. Default root on upstream main only, not in 2026.09.06.

 | `foundation` | `foundation` | The classic root. Upstream describes it as the legacy selected Foundation root, retained for compatible complete compositions. Still a selectable complete root: `amplifier bundle use foundation`.

### Frontmatter Keys

 |

 | Key | Shape | Notes

 | `bundle.name` | string | Stable identifier and the `@namespace` used in mentions. Not the repository name.

 | `bundle.version` | string, default `"1.0.0"` |

 | `bundle.description` | string | Metadata only; never sent to the model.

 | `bundle.display_name` | string, optional | Human label; hosts show `display_name` or `name`.

 | `bundle.namespace_root` | relative path, optional | For a YAML in `behaviors/` whose `agents/` and `context/` live one level up.

 | `includes` | list | Each entry is `- bundle: <ref>` or a bare string `<ref>`.

 | `session` | dict | `orchestrator: {module, source, config}`, `context: {module, source, config}`, plus flags such as `raw: true`.

 | `providers`, `tools`, `hooks` | list of `{module, source, config}` | Validated as module lists.

 | `agents` | mapping | `include: [ns:agent-name]` and/or inline `name: {description, instructions, tools}`.

 | `context` | mapping | `include: [ns:path/file.md]` or direct `name: path`.

 | `spawn` | dict | `exclude_tools: [...]` or `tools: [...]` for spawned agents.

 Keys that do not exist

There is no top-level `name:`, `version:` or `extends:`. The loader reads only `bundle.*`, `includes`, `session`, `providers`, `tools`, `hooks`, `spawn`, `agents` and `context`; anything else, including a top-level `skills:` key, is silently ignored.

### Markdown Body and References

- The body becomes the bundle's instruction and is emitted first in the system prompt, ahead of every context file.

- It should contain only model-facing instruction and `@mention` pointers, not documentation about the bundle.

- Only the root bundle's body reaches the prompt. Bodies of included bundles are discarded (later replaces earlier).

 |

 | Where | Syntax | Example

 | Markdown body | `@namespace:path` | `@foundation:context/shared/common-system-base.md`

 | YAML (`context.include`, `agents.include`, `includes`) | `namespace:path`, no `@` | `foundation:behaviors/agents`

The two forms are not interchangeable: an `@` inside YAML fails silently. `context.include` propagates to bundles that include this one; body `@mentions` do not. Behaviors therefore use `context.include`, and roots use `@mentions`.

### `includes:` URI Forms

 |

 | Form | Example

 | Git HTTPS, branch | `git+https://github.com/microsoft/amplifier-bundle-python-dev@main`

 | Git with a subdirectory or file | `git+https://github.com/microsoft/amplifier-bundle-recipes@main#subdirectory=behaviors/recipes.yaml`

 | Git pinned to a full SHA (40 or 64 hex) | `git+https://github.com/org/repo@32d4052dad46016f91ce698646580473e4121344`

 | Git SSH | `git+ssh://git@github.com/org/repo@main`

 | Namespace path (same repository or a registered bundle) | `foundation:behaviors/sessions`

 | Namespace-relative path | `anchors-amp-dev:../anchors/bundle.md`

 | Registered name | `foundation`

 | Local path or directory | `./bundles/dev.md`, `/path/to/bundle/`

 | `file://` | `file:///path/to/bundle`

 | Zip archive | `zip+https://example.com/bundle.zip#subdirectory=path/inside`

Abbreviated SHAs are not treated as pins. Pinned sources are skipped by `amplifier update`. Bare relative module sources (`source: ./modules/foo`) are discouraged; use a git URL with `#subdirectory=` that points back at the bundle's own repository.

### Composition Rules

Bundles do not inherit in a chain. A bundle composes a list of includes: the registry composes the includes first, then the including bundle, so the includer wins.

 |

 | Section | Merge rule

 | `session`, `spawn` | Deep merge; later wins for scalars

 | `providers`, `tools`, `hooks` | Merge by module ID; the same ID deep-merges config, a new ID is appended

 | `agents` | Merge by agent name; later wins

 | `context` | Accumulates; keys are prefixed with the bundle namespace

 | Instruction (markdown body) | Replaced; later wins

 | List-valued module config (for example skill sources) | Accumulates with de-duplication, parent first

### Bundle Settings

The CLI stores bundle choices in `settings.yaml` under the `bundle` key. Use the commands rather than editing by hand.

 |

 | Key | Type | Meaning | Written by

 | `bundle.active` | string | The primary bundle selected for sessions | `amplifier bundle use <name>`

 | `bundle.added` | map of name → URI | A registration: makes a bundle selectable by name. Does nothing until selected. | `amplifier bundle add <uri> [--name alias]`

 | `bundle.app` | list of URIs | App bundles: composed onto every session after the primary bundle. Not selectable; always on. This is how behaviors are installed into an existing host. | `amplifier bundle add <uri> --app`

 yaml
 Copy

`# ~/.amplifier/settings.yaml (global scope)
bundle:
 active: <bundle-name>
 added:
 <name>: <uri>

 - <uri>`
```

Settings scopes merge global → project → local → session, and the project scope is the exact working directory (no upward search). Providers are not part of the bundle keys: provider instances live under `config.providers`, each with `module`, `source`, optional `id`, and a `config` holding `default_model`, `priority` and `api_key: ${ENV_VAR}`.

### Storage Structure

Sessions persist at `~/.amplifier/projects/<project-slug>/sessions/<session-id>/`. The project slug is the working directory with path separators replaced by `-`, for example `/home/user/repos/myapp` becomes `-home-user-repos-myapp`.

 |

 | File | Contents

 | `transcript.jsonl` | Conversation history (with a `transcript.jsonl.backup`)

 | `events.jsonl` | Event log; copied on fork unless `--no-events`

 | `metadata.json` | Session metadata (with a `metadata.json.backup`)

 | `config.md` | Configuration snapshot

 | `settings.yaml` | Optional session-scope settings, written by in-session commands such as `/allowed-dirs add`

The interactive prompt history is kept one level up, at `~/.amplifier/projects/<project-slug>/repl_history`.

Agents are specialized configurations that run as sub-sessions for focused tasks. An agent is a bundle: same file format, with a `meta:` frontmatter block instead of `bundle:`. Agents are addressed as `bundle:agent`.

### Using Agents

There is no `@agent` prefix. The model delegates by calling the `delegate` tool, so ask in plain language. The interactive prompt is `>`.

 bash
 Copy

`# Interactive mode: ask for the agent by name
> Use the explorer agent to describe the architecture of this project
> Have the bug-hunter agent look for issues in the authentication module

# In a session
/agents

# List and show agents
amplifier agents list # Agents from the default bundle
amplifier agents list -b foundation # Agents from a specific bundle
amplifier agents show foundation:explorer
amplifier agents dirs`
```

### How Agents Work

- The model calls `delegate` with an `instruction` and an `agent` (`'foundation:explorer'`, `'self'`, or a bundle path)

- A sub-session is created with the agent's tools and instructions

- The sub-session executes the request

- The result and the sub-session ID return to the main session; passing `session_id` to a later `delegate` call resumes it

 |

 | `delegate` parameter | Meaning

 | `instruction` | Required. What the agent should do.

 | `agent` | `bundle:agent` name, `'self'`, or a bundle path

 | `session_id` | Resume an earlier sub-session

 | `context_depth` | `none` | `recent` | `all` (default `recent`)

 | `context_turns` | Number of turns for `recent` (default 5)

 | `context_scope` | `conversation` | `agents` | `full`

 | `model_role`, `provider_preferences` | Model selection for the sub-session. `model_role` is resolved by the routing matrix; `provider_preferences` wins when both are present.

Spawned agents cannot delegate further by default. The older `task` tool (module `tool-task`) is legacy; `delegate` (module `tool-delegate`, in the foundation repository) replaces it.

### Custom Agents

Write a standalone agent file (for example `agents/security-auditor.md`) and declare it in a bundle's or behavior's `agents:` section. `meta.description` is the only thing the delegating model sees when choosing an agent, so keep it short and specific (upstream caps it at 600 characters). The markdown body is the agent's instructions.

 markdown
 Copy

`---
meta:
 name: security-auditor
 description: |
 Use PROACTIVELY for vulnerability assessment and code auditing.
 Reviews directly without delegating.
 model_role: security-audit

agents: none

tools:
 - module: tool-filesystem
 - module: tool-bash
---

You are a security auditor...`
```

 yaml
 Copy

`# In the bundle or behavior that ships the agent (bundle.name: my-bundle)
agents:
 include:
 - my-bundle:security-auditor # loads agents/security-auditor.md`
```

In an agent file, a top-level `agents:` key with a string or list value controls which sub-agents that agent may call: `agents: none`, `agents: all`, or `agents: [explorer, bug-hunter]`.

### Agent Search Path

Agents load from: `.amplifier/agents/` (project) → `~/.amplifier/agents/` (user) → the named bundle → all discoverable bundles. `amplifier agents dirs` notes that agents are now primarily defined within bundles rather than standalone directories.

 `amplifier agents list`List agents from the default bundle (`-b` for another bundle)
 `amplifier agents show <bundle:agent>`Agent details, e.g. `foundation:zen-architect`
 `amplifier agents dirs`Show agent search directories

### Write Access

 `amplifier allowed-dirs list`Directories the AI can write to, with their scope
 `amplifier allowed-dirs add <path>`Allow writes (`--local` | `--project` | `--global`, default global)
 `amplifier allowed-dirs remove <path>`Remove an allowed path
 `amplifier denied-dirs list`Directories the AI is blocked from writing to
 `amplifier denied-dirs add <path>`Block writes; denied paths take priority over allowed paths
 `amplifier denied-dirs remove <path>`Remove a denied path

### Notifications

 `amplifier notify status`Show current notification settings
 `amplifier notify desktop --enable`Desktop/terminal notifications (`--disable`, `--show-preview`, ...)
 `amplifier notify ntfy --enable`ntfy.sh push notifications; prompts for the topic, stored in `keys.env` (`--server`)
 `amplifier notify reset --all`Reset notification settings (`--desktop`, `--ntfy`)

### Sources (Dev)

 `amplifier source list`List source overrides (modules and bundles)
 `amplifier source add <id> <path-or-uri>`Override where a module or bundle loads from (`--module` / `--bundle` force the type)
 `amplifier source remove <id>`Remove an override
 `amplifier source show <module-id>`Show the resolution path for a module

### System

 `amplifier init`Interactive setup: manage providers and routing
 `amplifier update`Update Amplifier (`-y`, `--force`, `-v`)
 `amplifier update --check-only`Check for updates without installing
 `amplifier version`Show version as `YYYY.MM.DD-<sha>` (`-v` adds install type)
 `amplifier reset`Reinstall and reset selected data; interactive, clears cache and registry by default
 `amplifier reset --dry-run`Preview what would be removed
 `amplifier reset --remove cache -y`Remove only the cache (`--preserve`, `--full`, `--no-install`)
 `amplifier doctor`Passive configuration check. Upstream main only, not in 2026.09.06
 `amplifier --help`General help

Scope flags come in two styles. `--local | --project | --global`: `bundle use`/`clear`, `module add`/`remove`, `source`, `allowed-dirs`, `denied-dirs`, `notify`. `--scope [global|project|local]`: `provider add`/`edit`/`list`/`manage`, `routing use`/`manage`, `module override`. Project and local scopes are unavailable when the working directory is your home directory. Most `list` and `show` commands accept `--format [text|json]` (experimental), `--detailed` and `--compact`.

The interactive prompt is `>` (with an active mode it becomes `[plan]>`). The installed build has 17 built-in slash commands:

 |
 | Command | Description | Forms

 | `/status` | Show session status |

 | `/tools` | List available tools |

 | `/agents` | List available agents |

 | `/mode` | Set or toggle a mode | `/mode`, `/mode <name> [on|off]`, `/mode off`, `/mode info <name>`

 | `/modes` | List available modes |

 | `/provider` | (experimental) Show or pin the conversation-scope provider | `/provider`, `/provider use <name>`, `/provider auto`, `/provider test <name>`, `/provider models <name>`

 | `/goal` | Set a goal condition and auto-continue until satisfied | `/goal <condition>`, `/goal --max-turns N <condition>`, `/goal clear`

### Configuration Files

Most specific wins. Settings are deep-merged in the order global → project → local → session, and CLI flags override them for one invocation.

 |
 | File | Scope | Purpose

 | `~/.amplifier/settings.yaml` | Global | User defaults

 | `.amplifier/settings.yaml` | Project | Team-shared settings (committed)

 | `.amplifier/settings.local.yaml` | Local | Machine-specific (gitignore it)

 | `~/.amplifier/projects/<slug>/sessions/<id>/settings.yaml` | Session | Highest precedence; written by in-session commands such as `/allowed-dirs add`

 | `~/.amplifier/keys.env` | Global | API keys and the ntfy topic. Secrets are never written to `settings.yaml`; provider entries hold `${VAR}` placeholders.

### Settings Keys

The top-level keys the CLI reads, with the command that writes each. Prefer the commands to hand-editing.

 yaml
 Copy

 added: # amplifier bundle add

### Directory Layout

`~/.amplifier/
├── settings.yaml # global scope settings
├── keys.env # API keys and ntfy topic
├── registry.json # bundle registry state (derived; regenerates)
├── cache/ # downloaded bundles and modules, dirs named <repo>-<hash>
├── bundles/ # user-level local bundles
├── routing/ # user-authored routing matrices
└── projects/
 └── <project-slug>/
 ├── repl_history # interactive prompt history
 └── sessions/
 └── <session-id>/ # transcript.jsonl, metadata.json, events.jsonl, config.md

<project>/.amplifier/
├── settings.yaml # project scope
├── settings.local.yaml # local scope
└── bundles/ # project-level local bundles`
```

`amplifier reset` categories map to this layout: `projects`, `settings`, `keys`, `cache`, `registry`. The default removal set is `cache` and `registry`. There is no `~/.amplifier/module-cache/` directory.

 Tips

- Pipe input: `cat file.py | amplifier run`. Standard input is read only when no prompt argument is given; to combine a prompt with a file use `amplifier run "Explain @file.py"`.

- JSON output for scripting: `amplifier run --output-format json "What is 2+2?"`

- Verbose output: `-v` or `--verbose`

- Reference files with `@path`, `@project:path`, `@user:path` or `@namespace:path`

- See what a bundle pulls in: `amplifier bundle show <name>`

## What Changed Since May 2026

The ecosystem roughly doubled in public repositories between May and November 2026. The shape of the growth matters more than the count:

 |

 | Change | What it means

 | Default root bundle (version-sensitive: `anchors` or `anchors-amp-dev`) | The upstream README now says Anchors is the default and calls `foundation` "a selectable complete root". Anchors lives inside `amplifier-foundation` (`bundles/anchors`), not in its own repo. The default depends on the CLI version. CLI build `2026.09.06` reports `anchors (default)`; upstream `main` has since moved the default to `anchors-amp-dev`, a thin root that includes Anchors. Sources, both verified in `microsoft/amplifier-app-cli`: `anchors` at 569c9b8, `amplifier_app_cli/commands/run.py#L335-L337`; `anchors-amp-dev` at 9a053f5, `amplifier_app_cli/lib/bundle_loader/discovery.py#L31`. No switch date is established.

 | Behaviors are the unit you add | The quick start now adds a behavior to the existing host (`amplifier bundle add '...#subdirectory=behaviors/recipes.yaml' --app`) instead of switching root bundles.

 | The kernel has more than Python bindings | `amplifier-core` is described upstream as a native Rust kernel with Python bindings and Node/C-ABI interfaces in the same repository. Upstream notes that binding source being present does not establish released artifacts.

 | Unified | A local, authenticated web workspace for chat, voice, and work, with terminal and macOS clients.

 | amplifier-agent | An embeddable engine with Python/TypeScript bindings and HTTP and ACP faces, plus apps and automation built on it.

 | Constellation | Independent persistent agents speaking ACP, with a standalone Rust runtime that is separate from Core-loaded loop modules.

 | Smart Tools | A new packaging kind: a specification, a conformance kit, a catalog, and library-first CLIs any agent can use.

 | Profiles and collections are formally deprecated | Upstream now lists `amplifier-profiles`, `amplifier-collections`, `amplifier-config`, and the `amplifier-collection-*` repos under "Deprecated Components", replaced by bundles.

 | Install command | Upstream shows `uv tool install git+https://github.com/microsoft/amplifier` (no `@main`).

### Token Tracker

 Copy

Monitor and log token usage across provider calls. `provider:response` is the orchestrator-contract event (`{provider, response, usage}`); the installed `loop-streaming` does not emit it, and providers emit `llm:response` instead, so register for that. In `provider-anthropic` 1.0.0 the `llm:response` payload is `{provider, model, duration_ms, status, usage}`, where `usage` carries `input_tokens`, `output_tokens`, `cost_usd` (a string, or `None` when unavailable) and, when present, `cache_read_tokens` and `cache_write_tokens`. An error response has `status: "error"` and no `usage`. Other providers may differ.

`from amplifier_core.models import HookResult

async def track_tokens(event, data) -> HookResult:
 """Log token usage from provider responses."""
 if event == "llm:response" and data.get("status") == "ok":
 usage = data.get("usage") or {}
 tokens = usage.get("input_tokens", 0) + usage.get("output_tokens", 0)
 cost = usage.get("cost_usd") # string, or None when unavailable
 print(f"Used {tokens} tokens (cost_usd: {cost})")
 return HookResult(action="continue")`
```

 Output

Used 1523 tokens (cost_usd: 0.0152)
```

### PII Redaction

 Copy

Flag PII-looking text in streamed output so you can log or alert on it. This observes only; it does not redact or block anything.

`import re
from amplifier_core.models import HookResult

PATTERNS = {
 "email": re.compile(r"[\w.-]+@[\w.-]+\.[a-z]{2,}"),
 "ssn": re.compile(r"\b\d{3}-\d{2}-\d{4}\b"),
 "phone": re.compile(r"\b\d{3}[-.\s]?\d{3}[-.\s]?\d{4}\b"),
}
findings: list[str] = []

async def flag_pii(event: str, data: dict) -> HookResult:
 text = str(data.get("delta", ""))
 for kind, pattern in PATTERNS.items():
 if pattern.search(text):
 findings.append(kind) # log or alert here instead
 return HookResult(action="continue")

# session.coordinator.hooks.register("content_block:delta", flag_pii, name="pii-flag")`
```

 Output

Delta: "Contact john@email.com or 555-123-4567"
findings == ["email", "phone"]
```

Limits: patterns are illustrative and miss many formats, and a phrase can be split across deltas. A `modify` result on `content_block:delta` only changes the data later handlers see (it replaces the whole dict, so copy it first). Whether the display or transcript uses it depends on the emitting module, so do not rely on it as a redaction or security boundary. ### Real-time Cost Tracking

 Copy

Monitor API costs in real-time with a budget stop. Checked against `provider-anthropic` 1.0.0 and `loop-streaming` 1.0.0: `llm:response` carries `model`, `usage.input_tokens` and `usage.output_tokens`, but the provider ignores the hook result for that event, so a `deny` there does nothing. The orchestrator does honor `deny` on `provider:request`, so the budget is enforced before the next call. Register the hook for both events; other providers may use different payload keys.

`from amplifier_core.models import HookResult

class CostTracker:
 # Per-1K-token prices: fill in from your provider's price list
 PRICING = {
 "<model>": {"input": 0.003, "output": 0.015},
 }

 def __init__(self, budget: float = 10.0):
 self.budget = budget
 self.spent = 0.0

 def track(self, model: str, input_tokens: int, output_tokens: int):
 rates = self.PRICING.get(model, {"input": 0.01, "output": 0.03})
 cost = (input_tokens * rates["input"] +
 output_tokens * rates["output"]) / 1000
 self.spent += cost
 return cost

tracker = CostTracker(budget=5.0)

async def cost_hook(event, data) -> HookResult:
 if event == "llm:response" and data.get("status") == "ok":
 usage = data.get("usage") or {}
 cost = tracker.track(
 data.get("model", "unknown"),
 usage.get("input_tokens", 0),
 usage.get("output_tokens", 0)
 )
 print(f"Cost: \${cost:.4f} | Total: \${tracker.spent:.2f}")

 elif event == "provider:request" and tracker.spent >= tracker.budget:
 # Blocks the next provider call
 return HookResult(action="deny", reason="Budget exhausted")

 return HookResult(action="continue")`
```

 Output

Cost: $0.0234 | Total: $4.89
Cost: $0.1156 | Total: $5.01
Operation denied: Budget exhausted
```

# Philosophy

The design principles and mindset that separate deliberate AI-augmented engineering from unconstrained generation.

 Why Philosophy Matters

Amplifier is not just a tool — it is a way of thinking about software construction. Understanding why the system is designed this way turns every interaction from guesswork into intent.

## Overview

Amplifier is built on a single foundational premise:

 "The kernel provides mechanisms. Modules provide policy. The human provides intent."

This means the core runtime stays minimal and stable while all interesting behavior lives at the edges — in modules, bundles, and agent configurations that can evolve rapidly without destabilizing the foundation. Every architectural decision in Amplifier can be traced back to this principle.

The practical consequence: an Amplifier session is a composition of explicit, inspectable, swappable pieces. Nothing is hidden. Nothing is magic. If something behaves unexpectedly, you can read exactly why — in the bundle, the module code, or the hook chain.

## The Seven Pillars

These are the first-principles from which all Amplifier design decisions follow. They are not marketing claims — they are constraints that have been held even when they made individual features harder to build.

### 1. Mechanism, Not Policy

The kernel provides capability; modules decide behavior. If two teams might want something to work differently, it belongs in a module — not in the core. This is the single most important principle: it is why `amplifier-core` stays small (about 6,600 lines of Rust by upstream's count, not recounted here) and the ecosystem is unbounded.

Ask yourself: "Could a different team legitimately want the opposite?" If yes → module.

### 2. Ruthless Simplicity

As simple as possible, but no simpler. Every abstraction must pay rent. Code you don't write has no bugs. When choosing between a clever solution and a boring one, choose boring. Complexity is a tax paid on every future modification.

The test: could a new contributor understand this in under 60 seconds? If not, simplify.

### 3. Bricks and Studs (Modular Design)

Every module is a self-contained brick with a public contract (studs) and a private interior. The interior can be regenerated entirely — from spec alone — without breaking any connector. The contract is sacred; the implementation is disposable.

Prefer regeneration over line-editing. If you're patching internals, the boundary is wrong.

### 4. Text-First, Inspectable Surfaces

All configuration, all context, all state is human-readable, diffable, and versionable. No hidden globals. No opaque binary state. If you can't `cat` it and `diff` it, the design needs revisiting. Observability is not a feature — it is a requirement.

JSONL logs, YAML and markdown bundles, markdown agents — every surface is a text file you can read and version.

### 5. Event-First Observability

If it matters, it emits an event. Most hooks only observe; a hook can also deliberately deny, modify, inject context or ask the user. The event stream is the single canonical record of what happened in a session. Everything from security auditing to memory capture to UI streaming runs on this same bus.

The event bus is not a side-channel — it is the primary communication surface between components.

### 6. Composition Over Configuration

New behavior comes from plugging in a different module, not from toggling flags in a massive config matrix. Amplifier avoids "configuration explosion" — the gradual accumulation of boolean toggles that each individually make sense but together create an incomprehensible state space.

If you need a feature flag, consider whether a new module (or a behavior) would be cleaner.

### 7. Don't Break the Edges

Backward compatibility in kernel contracts is sacred. Modules depend on the kernel; the kernel does not depend on modules. Additive evolution only, with clear deprecation paths and long sunset periods. The cost of a breaking change is paid by every module author in the ecosystem.

Add new APIs freely. Rename existing ones only with a long migration window and a compatibility shim.

## Vibe Coder vs Amplifier Coder

The term "vibe coding" describes a real and valid pattern: using an AI assistant to generate code through free-form conversation, accepting outputs that feel right without deeply inspecting them. It is fast, low-friction, and genuinely useful for throwaway scripts, prototypes, and exploration.

Amplifier is designed for a different mode — one that uses AI at the same level of leverage but with architectural intentionality. The distinction is not about effort or rigour for its own sake. It is about what kind of leverage compounds over time.

 |

 | Dimension
 | Vibe Coder
 | Amplifier Coder

 | Orientation
 | Output-oriented: "Does this run?"
 | Intent-oriented: "Does this reflect the right design?"

 | Relationship with AI
 | AI as author; human as acceptor
 | AI as crew; human as director

 | Module boundaries
 | Organic — emerge from generation
 | Deliberate — defined before implementation

 | Context management
 | One long conversation; hope the AI remembers
 | Explicit context injection; structured bundles and behaviors

 | Error handling
 | "Ask AI to fix it" until it works
 | Systematic: hooks, observability, then targeted fix

 | Spec discipline
 | Spec emerges after code works
 | Spec drives code; code is the proof of spec

 | Reuse model
 | Copy-paste or re-generate
 | Composable modules with stable public contracts

 | Observability
 | Run it and see; print-debug
 | Event stream; structured hooks; JSONL logs

 | Velocity profile
 | Fast start, slows over time as system grows
 | Slower start, accelerates over time as modules compound

 | Best for
 | Throwaway scripts, exploration, demos
 | Production systems, long-lived codebases, teams

 ✅ When vibe coding is the right choice

Vibe coding is not bad — it is misapplied when used for production systems. For a one-off script, a personal experiment, or a first-pass prototype you'll throw away, free-form generation is faster and entirely appropriate. The Amplifier mindset does not require ceremony for every task. Match the tool to the time horizon.

## The Amplifier Coder Loop

In practice, the Amplifier development loop looks like this:

 1. Declare Intent

State what you want — in plain language. Use IDD decompose if the goal is complex.

 2. Spec the Boundary

Define the module contract before generating code. What goes in, what comes out, what errors are possible.

 3. Build in the Medium

Generate the real artifact — not a sketch of it. Test-first. Code last.

 4. Verify Against Intent

Does the artifact match what you declared in step 1? Not just "does it run" — does it do the right thing.

 5. Seal and Compose

Mark the module complete. It becomes a stable brick — referenced by others, never reached into.

## The Compounding Advantage

The core argument for the Amplifier approach over vibe coding is not that it is more correct on day one — it is that it compounds. Each module built with a clean contract becomes leverage for every future module. Each hook written with clear semantics becomes reusable in a new context. Each bundle composed from existing bricks takes minutes instead of days.

Vibe coding produces code. Amplifier coding produces a system that produces code.

 Zero-Vector Design Connection

This philosophy lines up with the Zero-Vector Design thesis: eliminate translation loss between vision and product by using AI agents as a crew — not an author. The comparison is this site's own; it is not a statement from the Amplifier documentation. For further reading, see `amplifier-bundle-zerovector`, a community bundle built on this approach with slash-command crew modes and recipes.

# Architecture & Developer Guides

Deep-dive documentation on Amplifier's architecture boundaries, module building, and system design.

## Architecture Boundaries

The single most important concept for Amplifier developers: what belongs where.

 Core Insight

Amplifier separates mechanism (how things work) from policy (what to do). This separation is what makes modules portable across applications.

 APPLICATION LAYER
 amplifier-app-cli, amplifierd, your-custom-app
 "Policy" - What to do, how to present, where to find things

 KERNEL LAYER
 amplifier-core (one implementation, many consumers)
 "Mechanism" - How to coordinate, dispatch, validate

 MODULE LAYER
 amplifier-module-* (many implementations, shared by apps)
 "Capabilities" - What can be done (tools, providers, hooks)

### Why This Matters

### When boundaries are respected

- Apps can share modules without conflict

- Kernel updates benefit all apps

- Modules work in any compliant app

- Testing is isolated and predictable

### When boundaries are violated

- Apps become fragile and hard to maintain

- Kernel bypasses create inconsistent behavior

- Modules only work in specific apps

- Bugs are hard to trace

### What Belongs Where

#### Application Layer Responsibilities

 |

 | Responsibility | Example | Why App Layer

 | UX Systems | `CLIApprovalSystem`, `CLIDisplaySystem` | Apps decide how to show things

 | Module Resolution Policy | `AppModuleResolver` | Apps decide where to find modules

 | Settings Persistence | `~/.amplifier/settings.yaml` | Apps decide where to store config

 | Bundle Loading | `load_bundle()`, `BundleRegistry` (amplifier-foundation) | Apps decide what configurations exist

 | @Mention Processing | `AppMentionResolver` | Apps decide what @mentions mean

 | Capability Registration | `session.spawn`, `broadcast` | Apps inject their behaviors

Key principle: If it touches the user or filesystem, it's app-layer.

#### Kernel Layer Responsibilities

 |

 | Responsibility | Example | Why Kernel Layer

 | Session Lifecycle | create, initialize, execute, cleanup | Standard lifecycle for all apps

 | Module Coordination | `ModuleCoordinator.mount()` | Standard way to compose modules

 | Hook Dispatch | `HookRegistry.emit()` | Standard event ordering

 | Capability Registry | `coordinator.register_capability()` | Standard extension point

 | Config Validation | Requires `session.orchestrator` and `session.context`; full structural checks via `amplifier_core.validation.MountPlanValidator` | Standard contract enforcement

Key principle: If it's about coordinating modules, it's kernel-layer.

#### Module Layer Responsibilities

 |

 | Responsibility | Example | Why Module Layer

 | Tool Execution | `tool-filesystem`, `tool-bash` | Reusable actions

 | Provider Communication | `provider-anthropic` | LLM API abstraction

 | Hook Behavior | `hooks-logging`, `hooks-approval` | Reusable event handling

 | Orchestration Logic | `loop-streaming` | Execution patterns

 | Context Management | `context-simple` | Message storage strategies

Key principle: If it's a reusable capability, it's module-layer.

## The Boundary Test

Ask these questions to determine where code belongs:

 "Does this need to know about the user interface?"

 Yes → Application Layer
 Code that knows about console, WebSocket, etc.

 No → Kernel or Module Layer
 Code that just coordinates or provides capability

 "Does this define HOW to do something vs WHAT to do?"

 HOW (mechanism) → Kernel Layer
 How hooks dispatch, how modules coordinate

 WHAT (policy) → Application Layer
 What hooks to load, what modules to use

 "Could another app use this unchanged?"

 Yes → Module Layer
 Reusable tool, hook, or provider

 No → Application Layer
 App-specific code (e.g., WebSocket transport)

## Correct Patterns

### Pattern 1: Capability Injection

Apps provide transport; modules use it without knowing the details.

 ✓ CORRECT

`# APP LAYER - registers capability
async def desktop_broadcast(event: str, data: dict):
 await websocket.send_json({"type": event, **data})

session.coordinator.register_capability("broadcast", desktop_broadcast)

# MODULE LAYER - uses capability abstractly
async def on_event(event: str, data: dict):
 broadcast = coordinator.get_capability("broadcast")
 if broadcast:
 await broadcast(event, data) # Works for any transport!`
```

### Pattern 2: Bundle Loading

Apps load bundles; foundation resolves modules.

 ✓ CORRECT

`# APP LAYER - decides what bundle to load
bundle = await load_bundle(
 "git+https://github.com/microsoft/amplifier-foundation@main"
 "#subdirectory=bundles/anchors/bundle.md"
)

# FOUNDATION - resolves sources, downloads and activates modules
prepared = await bundle.prepare()

# KERNEL LAYER - the session mounts the modules on its coordinator
session = await prepared.create_session()`
```

### Pattern 3: Event Handling

Kernel dispatches; modules react; apps display.

 ✓ CORRECT

`# ORCHESTRATOR MODULE - emits; the kernel's HookRegistry dispatches
await coordinator.hooks.emit(
 "tool:post",
 {"tool_name": "bash", "tool_input": tool_input, "tool_result": result},
)

# MODULE LAYER - logs the event
async def log_tool_post(event, data):
 logger.info(f"Tool {data['tool_name']} completed")
 return HookResult(action="continue")

# APP LAYER - displays to user
async def show_tool_post(event, data):
 console.print(f"✓ {data['tool_name']}") # CLI-specific display
 return HookResult(action="continue")`
```

## Anti-Patterns to Avoid

### ❌ Kernel Bypass

 ✗ WRONG

`# App calling provider directly, bypassing kernel
response = await anthropic_client.messages.create(...)`
```

 ✓ CORRECT

`# App goes through session
result = await session.execute(prompt)`
```

### ❌ Module with Transport Knowledge

 ✗ WRONG

`async def stream_hook(event, data):
 await websocket.send_json(data) # Module shouldn't know this!
 return HookResult(action="continue")`
```

 ✓ CORRECT

`async def mount(coordinator, config=None):
 async def stream_hook(event, data):
 broadcast = coordinator.get_capability("broadcast")
 if broadcast:
 await broadcast(event, data)
 return HookResult(action="continue")

 coordinator.hooks.register("tool:post", stream_hook, name="stream")`
```

### ❌ App Reimplementing Kernel Logic

 ✗ WRONG

`# App has its own orchestrator loop
while True:
 response = await provider.complete(messages)
 if response.tool_calls:
 for call in response.tool_calls:
 result = await tools[call.name].execute(call.input)
 messages.append(...)`
```

 ✓ CORRECT

`# App uses session.execute()
result = await session.execute(prompt)`
```

## Module Builder Guide

Authoritative guide for creating Amplifier modules.

 Quick Reference

- Git is the registry

- Entry-point key = Module ID (non-negotiable)

- Modules reach users through bundles: a behavior lists the module under `tools:` / `hooks:` with a `source:`

- CLI is optional

### Module Types

 |

 | Type | Protocol | Mount Point | Examples

 | Tool | `Tool` | `tools` | filesystem, bash, web, search

 | Hook | handler `(event, data) → HookResult` | none: `coordinator.hooks.register()` | logging, approval, redaction

 | Provider | `Provider` | `providers` | anthropic, openai, azure-openai

### pyproject.toml (CRITICAL)

 Copy

`[project]
name = "amplifier-module-tool-myfeature"
version = "0.1.0"
description = "My feature tool for Amplifier"
requires-python = ">=3.11"
dependencies = ["amplifier-core"]

[project.entry-points."amplifier.modules"]
# CRITICAL: Entry-point key IS the module ID

[build-system]

```

 Non-negotiable Rules

- Entry-point key (`tool-myfeature`) = Module ID used everywhere

- Value points to `mount` function, not a class

- Naming convention: `tool-*`, `hooks-*`, `provider-*`, `context-*`, `loop-*`

- The entry-point group is `amplifier.modules` for every module type

### The mount() Function

 Copy

`# amplifier_module_tool_myfeature/__init__.py

from typing import Any
from .tools import MyFeatureTool

async def mount(coordinator, config: dict[str, Any] | None = None):
 """Mount this module's tools on the coordinator.

 Args:
 coordinator: The kernel's module coordinator
 config: Optional configuration from the bundle's module entry

 Returns:
 None, or a cleanup callable that the kernel calls at teardown.
 """
 config = config or {}

 # Create tool instance with config
 tool = MyFeatureTool(
 storage_path=config.get("storage_path", "~/.amplifier/myfeature.db"),
 max_items=config.get("max_items", 1000),
 )

 # Mount each tool by name on the "tools" mount point
 await coordinator.mount("tools", tool, name=tool.name)

 # Hook modules register handlers instead:
 # coordinator.hooks.register("tool:pre", handler, priority=0, name="my-hook")
 return None`
```

### Common Mistakes

 ✗ Wrong Entry Point

`# WRONG - points to class, not mount function
tool-myfeature = "amplifier_module_tool_myfeature:MyFeatureTool"

# CORRECT - points to mount function
tool-myfeature = "amplifier_module_tool_myfeature:mount"`
```

 ✗ Returning the Instance Instead of Mounting It

`# WRONG - returns the tool; a non-callable return value is ignored
async def mount(coordinator, config=None):
 return MyTool() # Nothing gets mounted!

# CORRECT - mounts on the coordinator; returns None or a cleanup callable
async def mount(coordinator, config=None):
 tool = MyTool(config or {})
 await coordinator.mount("tools", tool, name=tool.name)`
```

### Capability Injection Pattern

Modules must be transport-agnostic. They request capabilities abstractly; the app provides implementations.

 ✓ CORRECT: Request capability, app provides it

`# In module mount()
async def mount(coordinator, config=None):
 async def streaming_hook(event, data):
 # Request a capability by NAME, not by importing app code.
 # Look it up when the event fires: the app may register it after mount().
 broadcast = coordinator.get_capability("broadcast") # None when absent
 if broadcast:
 await broadcast(event, data)
 return HookResult(action="continue")

 coordinator.hooks.register("content_block:delta", streaming_hook, name="streaming")

# In app startup
def setup_session(session):
 # App registers the capability with its transport
 session.coordinator.register_capability("broadcast", websocket_broadcast)
 # Module gets websocket_broadcast when it asks for "broadcast"`
```

 ✗ WRONG: Module imports app/transport code

`# WRONG - module knows about WebSocket
from my_app.websocket import broadcast_to_clients

async def mount(coordinator, config=None):
 hook = MyHook(broadcast_fn=broadcast_to_clients) # Tight coupling!`
```

 Why This Matters

The same module works unchanged in CLI apps (console output), web apps (WebSocket), desktop apps (IPC), or test harnesses (mock). The module never knows or cares which transport is used.

### Event Names Reference

 |

 | Event | When | Hook Can Block?

 | `session:start` | First `execute()` of a new session | No

 | `session:end` | During `cleanup()` | No

 | `prompt:submit` | User message received | No

 | `provider:request` | Before LLM API call | No

 | `provider:response` | After LLM response | No

 | `content_block:start` | Streaming block begins | No

 | `content_block:delta` | Streaming content chunk | No

 | `content_block:end` | Streaming block ends | No

 | `tool:pre` | Before tool execution | Yes

 | `tool:post` | After tool execution | No

 | `tool:error` | Tool execution failed | No

 | `orchestrator:complete` | Orchestration done | No

This is a subset of the 43 canonical events; see Reference → Events. Any handler may return `deny`, `modify`, `inject_context` or `ask_user`; whether that changes anything depends on the module that emitted the event, and `tool:pre` is the documented blocking point. `provider:response` is a contract event that the installed `loop-streaming` does not emit (providers emit `llm:response`). Event names match exactly, with no wildcards, and dispatch is fail-open: a handler that raises is logged and skipped.
